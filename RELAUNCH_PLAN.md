### The three things that matter

**1. The site is indexable and empty.** This is the worst state to be in. Google can crawl, see a
live page with the text "Nothing Found", and record that as the site's content. A dark site reads
better than a live, empty, indexable one.

**2. PHP 8.1 is out of support.** 8.1 stopped receiving security fixes in December 2025. Combined
with a WordPress build three years behind, this is an active, exploitable liability sitting on
your domain — independent of any content decision.

**3. There is no SEO layer at all.** Rank Math is gone, so there are no canonicals, no schema
markup, and no sitemap. Whatever gets built needs this from day one.

**Note on DNS:** earlier notes recorded nameservers at `DNS-PARKING.COM`, but the site resolves
and serves from Hostinger. Treat DNS state as *unverified* — confirm in the Hostinger panel before
any migration.

## 3. Tech stack decision: do not use WordPress

**Recommendation: static site generated by the existing pipeline. Remove WordPress.**

This is not a preference, it is what the content shape demands.

| Factor | WordPress | Static (pipeline output) |
|---|---|---|
| 1,000+ programmatic pages | Thousands of DB rows, slow queries, admin bloat | Just files |
| Daily regeneration | Awkward; needs import tooling | Rebuild and deploy, ~40 seconds |
| Version control | Content lives in MySQL, not git | Every page is diffable |
| Page speed (Core Web Vitals) | PHP render + plugin JS | Near-instant, CDN-served |
| Security surface | PHP, plugins, XML-RPC, REST, admin login | None — no server code to exploit |
| Schema / canonicals | Needs a plugin that keeps changing | Emitted directly in the template |
| Cost | Hostinger plan + maintenance | Cloudflare Pages free tier is sufficient |
| Your existing asset | — | **The pipeline already outputs exactly this** |

WordPress's strengths are editorial workflow and non-technical editing. Neither applies here: the
pages are generated from data, and they change on a cron, not a person's schedule.

**Keeping WordPress would mean discarding the pipeline you already have and rebuilding it as a
plugin — strictly worse on every axis.**

### Exception

If you want an editorial blog (occasional analysis pieces, not data pages), you have two clean
options:

- **Preferred:** add a `blog/` output to the pipeline. Static, versioned, same deploy.
- **If you want a real editor UI:** keep a headless CMS or a WordPress install at `/blog/` only,
  never at the root. This must not become the main site again.

Do **not** put the data pages in WordPress.

## 4. Target architecture

```
Git repo (github.com/<you>/toolsummary)
   ├── automation/mvp/          ← existing pipeline
   │     fetch → gate → history → build → QA → site/
   └── ...
        │
        ▼  CI on push (GitHub Actions) or cron automation
   Cloudflare Pages  ──►  toolsummary.com  (static, CDN, free)
        │
        ├── /model/{slug}/           662 pages
        ├── /compare/{a}-vs-{b}/     400 pages
        ├── /changes/                price movements
        ├── /history/{slug}/         charts
        ├── /sitemap.xml, /llms.txt
        └── (later) /api/v1/*        paid, separate service
```

**Hosting choice:** Cloudflare Pages. Free, global CDN, automatic HTTPS, deploys on git push, and
supports redirects and headers files. Netlify or Vercel are equivalent alternatives.

**Redirect handling:** the old URL structure is gone and Google has already deindexed it, so mass
301s are not required. But do **not** let old 404s return a 40KB "not found" page — configure a
proper 404 and a 301 map for any URL that ever had links (you mentioned <200 backlinks; get the
list from Search Console and 301 the ones that matter).
